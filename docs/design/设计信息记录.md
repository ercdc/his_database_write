# HIS 数据病历填充：设计信息记录

本文件用于持续记录来自医院、HIS 厂商、模型服务方的新增信息。每条信息应标明：事实、来源、是否已验证，以及它对当前设计的影响。

## 当前架构基线

当前 Demo 以 DeepSeek OpenAI 兼容接口验证了以下链路：

```text
Web API
  → 读取 HIS 数据（当前为本地 Fixture）
  → 业务 Skill 组装提示词、XML 模板、允许工具
  → 模型返回 write_first_course_xml tool_call
  → C# 工具执行 XML XSD 校验并写入 Output
```

当前模型通信实现位于：

```text
src/HisMedicalRecordFillDemo/Services/DeepSeekToolCallingClient.cs
```

它依赖 OpenAI 风格的 Chat Completions Tool Calling 协议，因此只能视为“外部模型适配的第一种实现”，不能直接假定与医院模型服务兼容。

### 设计判断

“模型是否医疗专用”与“是否支持 Tool Calling”不是同一件事。

Tool Calling 能否使用，取决于以下三层同时成立：

```text
底座模型
  是否能理解工具描述、生成结构化工具调用
      ↓
推理服务
  是否实现并对外暴露 tools / tool_choice / tool_calls 协议
      ↓
院方接入层
  是否允许本项目传入工具定义并接收模型工具调用结果
```

因此，即使医院部署的是医疗领域微调模型：

- 若其服务兼容 OpenAI Chat Completions，且支持 `tools`、`tool_choice`、`tool_calls`，当前 Tool Calling 设计可复用，只需新增医院模型客户端适配。
- 若模型能生成 JSON、但服务不支持 Tool Calling 协议，仍可让模型直接输出约定 JSON，例如 `{ "xml": "..." }`；C# 再执行 XML 校验和写入。这不是 Tool Calling，但可完成首次病程生成闭环。
- 若模型只能输出普通文本，则需要以提示词约束 XML 输出，并由 C# 从响应中提取/校验 XML。这是最后一种兼容路径，结构稳定性最弱，不应作为首选。

当前阶段不应根据“医疗专用模型”推断其能力，也不应提前删除 Tool Calling 设计。

## 需要向医院模型服务方确认的问题

### 一、服务与协议

1. 模型的名称、版本、上下文长度和最大输出长度是什么？
2. 服务入口是什么：HTTP API、SDK、MCP、gRPC，还是其他形式？
3. 是否兼容 OpenAI Chat Completions API？若兼容，具体兼容到哪个版本？
4. 是否支持流式响应？本项目首期不需要流式，但需知晓能力边界。

### 二、Tool Calling（本项目核心）

1. 请求体是否支持 `tools` 字段？
2. 是否支持 `tool_choice` 强制指定工具？
3. 响应中是否以 `tool_calls` 返回工具名称、调用 ID、JSON 字符串参数？
4. 模型工具调用后，是否支持继续发送 `role: tool` 的执行结果并完成下一轮对话？
5. 是否有 strict / JSON Schema 约束能力？支持的 JSON Schema 范围是什么？
6. 若是思考模型，工具调用时是否有额外要求，例如必须回传 reasoning 内容？
7. 院方是否禁止业务系统传入自定义工具定义？

### 三、医学能力与输出约束

1. 模型是否针对病历生成、临床文本或医院术语做过微调？
2. 模型是否允许按指定 XML 模板输出长文本？
3. 是否支持 JSON Mode 或结构化输出？
4. 单次请求允许的 HIS 数据长度是否足以容纳病案、医嘱、费用、报告？

## 最小验证用例

在接入真实 HIS 前，向医院模型服务执行一次独立验证。输入一个无患者隐私的测试请求，仅注册以下工具：

```json
{
  "type": "function",
  "function": {
    "name": "write_first_course_xml",
    "description": "写入首次病程 XML。",
    "parameters": {
      "type": "object",
      "properties": {
        "xml": { "type": "string" }
      },
      "required": ["xml"]
    }
  }
}
```

验证通过必须同时满足：

1. 模型响应包含工具名 `write_first_course_xml`；
2. 参数是可解析的 JSON，且具有 `xml` 字段；
3. 将工具执行结果以院方规定格式回传后，模型能正常完成第二轮响应；
4. 生成的 XML 能通过本项目的 XSD。

若第 1～3 项不能满足，应记录院方实际响应并选择“JSON 结构化输出”或“直接 XML 输出”模式，而不是修改病程业务规则来迁就协议差异。

## 对后续代码的影响

当前不修改 Demo 的业务 Skill、XML Schema、Tool Registry 和 XML 写入工具。后续只需要将模型服务层抽象为接口，例如：

```csharp
public interface IToolCallingModelClient
{
    Task<ToolCallingResult> RunAsync(
        SkillContext skill,
        string patientId,
        string visitId,
        CancellationToken cancellationToken);
}
```

当前的 `DeepSeekToolCallingClient` 是该接口的一种实现。医院 API 确认后：

- 协议兼容：新增 `HospitalToolCallingModelClient` 或通过配置复用现有 HTTP 实现；
- 仅支持 JSON：新增 `HospitalStructuredOutputClient`；
- 仅支持文本：新增 `HospitalXmlTextClient`。

模型适配层可以变化，但 `FirstCourseSkill`、`write_first_course_xml` 的工具定义和 C# XML 校验/写入应保持不变。
